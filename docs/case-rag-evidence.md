# RAG 답변의 출처 연결과 실패 처리

## 문제

기존 챗봇은 검색 결과가 없어도 `(관련 글 없음)`을 프롬프트에 넣어 답변 생성을 요청했다. 생성 비용이 발생하며, 답변이 수집된 글을 근거로 작성됐는지 사용자가 확인하기 어려웠다.

프론트엔드에는 출처 카드와 `citations` SSE 이벤트 처리가 이미 있었지만, 서버는 `delta`만 전송했다. 따라서 실제 API에서는 답변의 `[1]`과 원문 링크가 연결되지 않았다. 여러 답변의 출처 카드도 동일한 DOM ID를 사용했다.

## 변경한 동작

1. 검색 결과가 없으면 고정 안내를 반환하고 답변 생성 API를 호출하지 않는다. 질문 임베딩 호출은 여전히 필요하다.
2. 검색 결과가 있으면 실제 DB의 제목, 원문 URL, 매체, 발행일을 `citations` 이벤트로 먼저 보낸다. 프롬프트와 출처 카드가 같은 배열 순서로 번호를 매긴다.
3. 이어서 기존 `delta` 이벤트와 `[DONE]`으로 답변을 전송한다. 기존 화면의 SSE 처리를 재사용한다.
4. 출처 카드 ID에 답변 ID를 포함해 후속 답변의 인용이 자기 카드로 이동한다. 제공된 출처 목록에 없는 인용 번호는 일반 텍스트로 표시한다.
5. 질의와 문서 임베딩은 동일한 검증 경로에서 768차원, 유한한 숫자, 비영벡터인지 확인한다. 잘못된 벡터는 DB에 보내지 않는다.
6. 임베딩·DB 장애는 빈 검색 결과로 바꾸지 않는다. 기존 오류 SSE 경로로 전달하며, 내부 오류 상세는 클라이언트에 노출하지 않는다. 문서 임베딩 실패도 기존 작업 재시도 경로를 유지한다.

## 재현 가능한 검사

외부 Gemini, Redis, PostgreSQL 없이 실행하는 회귀 검사다. 모델과 DB는 테스트 대역을 사용한다.

```sh
pnpm --filter @devbrief/api test --runInBand chat embedding
pnpm --filter @devbrief/web test src/components/inline-chat.test.tsx
```

| 시나리오 | 확인하는 동작 |
| --- | --- |
| 검색 결과 0개 | 안내 이벤트만 반환하고 `streamText` 호출 0회 |
| 검색 결과 2개 | 출처가 답변보다 먼저 전송되고 프롬프트와 번호·제목·URL이 일치 |
| 임베딩 또는 DB 오류 | 성공한 빈 검색으로 위장하지 않고 생성 호출 없이 오류 전파 |
| 잘못된 차원·0 벡터·NaN·Infinity·문자열·응답 없음 | 질의·저장 경로 모두 오류, 저장 SQL 미호출 |
| 두 번 질문한 뒤 두 번째 `[1]` 클릭 | 두 번째 답변의 출처로만 이동 |
| 제공되지 않은 `[99]` | 작동하지 않는 인용 버튼을 만들지 않음 |
| 출처 수신 뒤 생성 실패 | 불완전한 답변과 출처를 지우고 재시도 안내 |
| KST 자정 부근 발행일 | 기존 한국 날짜 기준 유지 |

## 검증의 한계와 다음 판단

이 검사는 출처 전달과 실패 분기를 검증한다. 실제 pgvector 검색 정확도, 모델 답변의 사실성, 운영 비용 감소율을 측정한 결과는 아니다. 출처 카드는 검색에 사용한 후보 글이며, 모델이 그 모든 글을 인용했다는 뜻은 아니다.

현재 검색은 코사인 거리 Top-K다. 임베딩이 있는 글이 존재하면 질문과 무관한 후보도 반환할 수 있다. 빈 검색 차단만으로 환각이 해결되지는 않는다. 실제 질문과 관련 글을 사람이 표시한 평가 자료를 확보한 뒤, 검색 순위·무관 질문 거절률을 측정해야 한다. 이번 변경에는 검증되지 않은 유사도 임계값을 추가하지 않았다.

기간·읽음 상태를 자연어에서 추출하는 검색 필터, 인용 문장 자체의 사실 검증, 실제 서비스 E2E는 별도 검증이 필요하다. 배포와 유료 모델 호출은 이 작업의 검증에 포함하지 않았다.
